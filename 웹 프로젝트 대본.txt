📋 추천 목차 구성 및 발표 전략
1. 프로젝트 개요 (Introduction)
문제 정의: "왜 이 프로젝트를 시작했는가?" (예: 잦은 약속 지각 문제 해결, 기존 캘린더 앱의 강제성 부족)

목표: 지각 방지를 위한 '게이미피케이션(Gamification)' 요소(페널티) 도입.

타겟 사용자: 약속이 많은 대학생 및 20대.

2. 아키텍처 및 정보 구조도 (Architecture & IA)
정보 구조도 (IA): Home -> Login -> User Home -> Register Flow로 이어지는 계층 구조 시각화.

데이터 흐름도 (Data Flow): 사용자 입력 -> 임시 저장소(localStorage) -> 최종 저장소로 이어지는 데이터 이동 과정 강조. (특히 3단계 등록 프로세스의 데이터 전달 방식 설명)









3. 기술 스택 (Tech Stack)
Frontend: HTML5, CSS3 (Tailwind CSS), JavaScript (ES6+).

Storage: LocalStorage API (서버리스 환경에서의 데이터 영속성 구현).

Tools: Vercel (배포), Git/GitHub (버전 관리).

강조점: 왜 React나 Vue가 아닌 Vanilla JS를 선택했는지? (기본기 강화, 가벼운 실행 환경, 빠른 프로토타이핑 등)





4. 주요 기능 및 시연 (Key Features & Demo)
핵심 기능 5가지:

회원가입/로그인: LocalStorage를 활용한 인증 시스템.

다크 모드: Tailwind CSS 기반의 테마 전환.

약속 등록 (3단계 프로세스): 직관적인 UX를 위한 멀티 스텝 폼.

약속 목록 및 D-Day: 실시간 D-Day 계산 및 정렬.

약속 수정/삭제: 데이터 무결성을 유지하며 수정하는 로직.

시연 영상 또는 스크린샷: 실제 작동 모습을 보여줍니다.

5. 개발 과정 및 트러블 슈팅 (Development Process)
가장 중요한 파트: 단순히 "만들었습니다"가 아니라 **"어떤 문제가 있었고 어떻게 해결했는지"**를 보여주는 것이 핵심입니다.

트러블 슈팅 사례 (예시):

문제: 등록 프로세스 중 페이지 이동 시 데이터가 날아가는 문제.

해결: tempData라는 임시 저장소를 활용하여 단계별 데이터를 유지하고 최종 단계에서 병합하는 로직 구현.

문제: 모바일 환경에서 버튼이 둥둥 떠다니는 UI 오류.

해결: absolute 대신 flexbox와 relative 포지셔닝을 사용하여 레이아웃 안정화.

6. 향후 계획 (Future Work)
백엔드 도입: Firebase나 Node.js를 도입하여 실제 서버 DB 연동.

실시간 기능: 친구 초대 및 실시간 위치 공유 기능.

PWA: 앱처럼 설치 가능한 웹 애플리케이션으로 고도화.

💡 발표 팁
시각 자료 활용: 아키텍처나 흐름도는 다이어그램으로 표현하면 훨씬 전문적으로 보입니다.

코드 리뷰: 핵심 로직(예: D-Day 계산 함수, 데이터 저장 로직)은 코드를 직접 보여주며 설명하면 기술적 역량을 어필하기 좋습니다.
















main.css와 tailwind.css로 사용한 이유에 대한 프롬프트 복붙
청중에게 설명할 때, **HTML에 직접 적는 Tailwind 방식(Utility-First)**과 **main.css로 분리하는 방식(Global/Complex)**을 구분해서 사용하는 이유를 다음과 같이 3가지 핵심 관점으로 설명하시면 좋습니다.🗣️ 발표용 설명 시나리오 (핵심 논리)1. "왜 HTML에 클래스를 길게 적나요?" (생산성 및 직관성)"지금 보시는 <h2> 태그처럼 text-5xl, mb-6 같은 클래스를 HTML에 직접 적는 방식은 '유틸리티 퍼스트(Utility-First)' 방식입니다.이 방식의 장점은 파일을 왔다 갔다 할 필요 없이, HTML만 보고도 디자인을 직관적으로 파악하고 빠르게 수정할 수 있다는 점입니다. 요소 하나하나의 **'개별적인 스타일'**을 지정할 때는 이 방식이 훨씬 효율적입니다."2. "그럼 main.css는 왜 따로 있나요?" (전역 관리 및 복잡도 격리)"하지만 모든 스타일을 HTML에 다 적을 수는 없습니다. 제가 main.css 파일을 따로 만들어 분리한 이유는 크게 두 가지입니다.첫째, 전역적인 설정(Global Settings) 때문입니다.폰트(@font-face)나 기본 배경색처럼 웹사이트 전체에 공통적으로 적용되어야 하는 규칙은 한 곳(main.css)에서 관리해야, 나중에 폰트를 바꿀 때 파일 하나만 수정하면 모든 페이지에 적용되기 때문입니다. (유지보수성)둘째, 코드의 복잡도를 낮추기 위해서입니다.애니메이션(@keyframes)이나 복잡한 커스텀 스타일은 HTML 클래스로 표현하기 어렵거나 코드가 너무 지저분해집니다. 이런 '복잡한 로직'은 CSS 파일로 격리시켜서 HTML 코드를 깔끔하게 유지하고자 했습니다."📝 요약 (발표 장표에 넣을 키워드 추천)이 내용을 장표에 요약해서 넣으신다면 다음 키워드를 추천합니다.구분Tailwind 클래스 (HTML 직접 작성)main.css (별도 분리)사용 목적개별 UI 컴포넌트의 빠른 스타일링사이트 전역 공통 규칙 및 복잡한 스타일 정의장점개발 속도 향상, 직관적인 수정유지보수 용이, 코드 재사용성 확보예시글자 크기, 여백, 색상 (text-5xl)폰트 정의(@font-face), 애니메이션(@keyframes)결론 멘트:"즉, 빠른 개발이 필요한 부분은 Tailwind의 유틸리티 클래스를 사용하고, 전체적인 관리와 복잡한 구현이 필요한 부분은 CSS로 분리하여 개발의 효율성과 코드의 관리 용이성 두 마리 토끼를 모두 잡는 전략을 선택했습니다."이렇게 설명하시면 비전공자나 Tailwind를 모르는 사람도 "아, 이유가 있어서 나눴구나!" 하고 명확하게 이해할 수 있을 거예요. 발표 잘 하세요! 👍
